# Lessons from the 0.0.6 release

What went wrong, what was found late, and what the next sign-off must check. Each item names the
check that would have caught it earlier.

## 1. The Welcome notebook (the demo) ships inside the executable

- The engine's `build.rs` embeds `docs/demo/DemoNotebook/html` into `notecraft.exe`. The MSI and the
  zip contain no demo folder. The app writes the notebook on first start.
- Check the built executable, not the files: `grep -c -a 'Ver <version>' notecraft.exe` must be
  1, and `Ver <previous>` must be 0.
- Check the first start on a fresh profile **from a working directory outside the repository**.
  Run the zip's `notecraft.exe` with `USERPROFILE` and `APPDATA` pointed at an empty folder, then
  check that `Documents\NoteCraft\welcome-to-notecraft` has 13 language folders and that
  `last_page` is `welcome-to-notecraft/00-start/welcome`.
- A test started from the repository folder uses the repository's `local/settings.toml`, because
  the app treats a folder with `Cargo.toml` or `local/` as a development checkout. That run proves
  nothing about a real install. Start the test with `-WorkingDirectory` set outside the repository.

## 2. Settings survive uninstall, and they hide first-run behaviour

- `%APPDATA%\NoteCraft\settings.toml` is not removed by uninstalling. An old copy with
  `welcome_added = "true"` and `privacy_welcome_seen = "true"` suppresses the Welcome notebook and
  the first-use privacy dialog. This is the most likely reason the VM showed no notebook and no
  dialog.
- The sign-off must say the clean-machine test deletes `%APPDATA%\NoteCraft` first, and that
  `Documents\NoteCraft` is empty.
- Fixed in this release: the first-start add depends on the folder being empty, not on the flag. A
  failure is shown in a message box, because the GUI build has no console.

## 3. A replaced demo must replace the old copy, not sit beside it

- `install` used to write into a numbered folder next to an old copy, and a failed write left a
  half-written folder. It now deletes the old `welcome-to-notecraft` folder and writes the bundled
  copy. A test covers the replacement.

## 4. Monochrome Fluent icons cannot be tinted light

- The Fluent SVGs use `fill="#212121"`. Egui's tint multiplies that colour, so a white tint leaves
  the icon black. Every "tinted" monochrome icon was only ever darkened.
- The fix writes the colour into the SVG before it is drawn (`icons::coloured_svg`). A visual check
  of the header and the ribbon in the regenerated screenshots is the test.

## 5. Opening a missing folder opens Documents

- On Windows, `explorer <path>` opens Documents when the path does not exist. The telemetry folder
  does not exist until a session writes to it, so "Open telemetry folder" showed the wrong place on
  a fresh install.
- The telemetry folder is now created before it is opened. `open_folder` refuses a missing folder.

## 6. The release workflow writes its own notes

- `.github/workflows/release.yml` drafts the release with fixed text and `--generate-notes`. It
  never reads `docs/releases/<version>/RELEASE_NOTES.md`, so the image and the highlights were
  missing from the draft.
- A relative image link (`0.0.6.jfif`) does not resolve on a release page. Use the absolute URL on
  `main` (`https://raw.githubusercontent.com/<repo>/main/docs/releases/<version>/<file>`).
- Workaround used for 0.0.6: `gh release edit v0.0.6 --draft --notes-file <file>` with the absolute
  image URL. The draft stayed unpublished.
- **Open:** change the workflow to read the notes file and rewrite relative image links. Until
  then, edit each draft body by hand.

## 7. The version appeared in too many places

- Before a release, search the whole repository for the previous version string:
  `git grep -n "0\.0\.5" -- ':!docs/releases' ':!vendor' ':!Cargo.lock'`. In this release it was in
  the README, the Welcome notebook source and its generated copies, a UI test, the OfficeIMO
  packaging example, `AGENTS.md`, and `docs/releasing.md`. `AGENTS.md` and `docs/releasing.md` were
  both still at the old version.
- Update the approved-version sentence in `AGENTS.md` and `docs/releasing.md` in the same change.

## 8. Installer and zip checks that caught real problems

- The MSI shipped **no notices** until this release: no NOTICE, ATTRIBUTION, or licence texts. The
  PDF renderer's MIT notice and the PDFium font licence were missing from both packages. Check the
  file list with an administrative install:
  `msiexec //a <msi> //qn TARGETDIR=<folder>`, then list the folder.
- Compare the executable hash across the MSI install, the zip, and the build output. They must be
  identical.
- Check the zip's entries with `System.IO.Compression.ZipFile`, and check `SHA256SUMS.txt` against
  `sha256sum`.
- `pwsh` is not installed on this machine. Run the packaging script with
  `powershell -NoProfile -ExecutionPolicy Bypass -File packaging/windows/package.ps1`.

## 9. Screenshots of a running window

- `scripts/capture-window.ps1` failed with `ExternalException` on this machine and wrote no file.
  Use the headless runner (`cargo xtask screenshots`) for shipped pictures. Use a real window
  capture only for a check the runner cannot show, and say when a capture failed.

## 10. Process

- The release workflow drafts a release from `workflow_dispatch` on `main`. It creates the tag and
  publishes nothing. The owner publishes by hand.
- Create the `release-<version>` label, as for earlier releases.
- Do not use `git commit --no-verify` or `git push --no-verify`. An amend with `--no-verify` slipped
  through in this release; re-run the hooks when it happens.
- Before saying a fix works, test the built artifact on a fresh profile. Several "fixed" claims in
  this release were checked only in the repository, which did not reproduce the VM's state.

## 11. Release draft images and links must resolve from the draft page

- An image can be attached to a draft release and still be missing from the rendered description.
  The body must contain an image embed, and its URL must be reachable by the renderer.
- A raw GitHub URL pinned to the release's target commit fails when the artwork was added to a
  later commit. Confirm the file exists at the URL's exact ref. Prefer a stable committed raw URL
  that returns HTTP 200, or a current release asset URL when its access behavior is verified.
- Rewrite all repository-relative links in the release body. They resolve in a repository file,
  but not necessarily in a GitHub release description.
- After editing a draft, inspect the final rendered preview, image URL, asset URLs, and current
  draft URL again. Drafts without a created tag can have an `untagged-*` URL; do not reuse an old
  draft URL in the notes or handoff.

## 12. Every platform artifact must match the release version

- A green desktop Packaging matrix does not prove that Android is packaged. Check the Android
  builder as a separate platform and require its NoteCraft APK artifact to pass the build and
  package-version checks before attaching it.
- Some external Android workflows select the latest stable NoteCraft release tag. A draft
  0.x release may not be a stable tag available to that workflow, so it can silently build the
  prior release. Verify the selected source ref and APK version instead of trusting the filename.
- If an Android build fails, record the concrete cause and leave the APK out. Never rename or
  describe an older APK as the current release.

## 13. A current demo source does not prove the hosted demo updated

- A website deployment can be cancelled during its long WebAssembly build. A successful source
  check and current notebook files do not prove Azure received that build.
- Trigger deployments when app code, crates, workspace version, web-build patches, demo source, or
  assets change. Do not cancel an in-progress production deployment when a later run is queued.
- Check the built and live WebAssembly for the workspace version. A user can still see an older
  notebook saved by the host, so verify the sample in a clean browser session too.

## 14. Align source and version across deployment pipelines

- Website deployment, desktop Packaging, GitHub Release, and Android builds are separate flows.
  A successful run in one does not update the others.
- Run desktop Packaging and Release from the same `main` commit. The Release workflow should reject
  a Packaging run from another commit, branch, or workflow and derive the tag version from the
  workspace manifest.
- Android is built externally today. Record its source commit, APK package version, signing
  certificate identity, and clean-install result separately. A filename alone is not proof.
- Check the live demo after deployment and use a clean browser profile when verifying its bundled
  Welcome notebook. Keep a release provenance record with one source SHA and matching version for
  each artifact.

## 15. Build both page formats, ship the HTML User Assistance notebook

- Generate HTML and CMGFM from the same authored demo source and keep format parity tests green.
- The User Assistance payload distributed on Windows, macOS, Linux, Android and the website is the
  HTML notebook only. Do not confuse app support for CMGFM with a requirement to ship a CMGFM copy
  of the Welcome notebook.
- Inspect each platform package and the website archive to confirm CMGFM files are absent.

## Checklist for the next sign-off

1. Grep for the previous version string, and update `AGENTS.md` and `docs/releasing.md`.
2. Rebuild the demo, run `cargo xtask demo-check`, and check the executable's version text.
3. Build the MSI and zip. Compare the SHA-256 of the executable across the MSI, the zip, and the
   build.
4. List the MSI and zip contents. The notices must be present.
5. Run the zip's `notecraft.exe` on a fresh profile, from outside the repository. Check the 13
   welcome pages and the last page.
6. Clean-machine test: delete `%APPDATA%\NoteCraft` and check that `Documents\NoteCraft` is empty.
   Install the MSI, start from the Start menu, check the notebook and the first-use dialog.
7. Run `cargo xtask ci` on the release branch.
8. Start the release workflow from `main`. Check the draft's body and image URL. Edit the body if it
   is generic.
9. For every body image, issue a request to the exact URL and check it in the rendered draft. Check
   that all relative repository links were rewritten, then refresh the draft URL after the final
   edit.
10. Verify one version-matched artifact per supported platform. Confirm Android's source commit,
    APK package version, signing identity, and install result separately from desktop packaging.
11. Confirm website, desktop artifacts, and Android all report the intended source/version; explain
    any platform that is still manual or missing from the release.
12. Owner's policy changed on 2026-11-07: verify both generated Welcome formats ship and the app
    refreshes its managed copy at startup. Preserve all sibling user notebooks.
13. Publish only when the owner says so.
