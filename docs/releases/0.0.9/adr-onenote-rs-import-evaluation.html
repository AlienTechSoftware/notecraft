Evaluate onenote.rs as the sole import backend

Evaluate a migration from the current import implementations to one Rust import path. Compare behavior before cutover, but ship only one production importer. This record authorizes evaluation only; it does not approve a production migration.

Proposed decision

Target one production importer

Evaluate onenote.rs as a replacement for both current routes: the in-repository parser used by import onenote and the OfficeIMO bridge used by the UI and CLI. During development, compare all implementations against the same synthetic cases. If the candidate passes every acceptance gate, cut over to it as the sole production importer and remove both old routes from the shipped app and packages. If it fails, do not cut over; choose one existing implementation in a revised decision. Do not ship dual backends, add a user-facing selector, or silently retry with a second parser.

Decision gate: migration is conditional on full tests, required import fidelity, license and dependency review, and measured release packages. Until then, this ADR approves evaluation only.

Conditional target; migration not yet approved

Context

The current UI routes imports through OfficeIMO. The CLI also exposes the in-repository notecraft-onenote parser and an OfficeIMO command. The target state is one shared production importer for the UI and CLI.

  • In-repository parser: import onenote uses notecraft-onenote for a folder tree of .one sections.
  • OfficeIMO project: the UI and CLI can invoke its separately packaged bridge. The Windows packaging script stages its self-contained runtime beside NoteCraft.
  • onenote.rs project: the local checkout exposes parsing for .one and .onetoc2; its onepkg Cargo feature enables .onepkg archive parsing.

The candidate's public model includes section color and content types for rich text, tables, images, embedded files, and ink. That model still needs to be mapped to NoteCraft's page, asset, color, and report behavior. API support alone is not proof of end-to-end fidelity.

Options considered

OptionDisposition
Adopt onenote.rs as the sole importerPreferred target, conditional on all evaluation gates.
Consolidate on OfficeIMOAlternative if onenote.rs does not pass its gates.
Build and maintain our own parserLeast favorable; pursue only if the other paths cannot meet product requirements.

Pros and cons

OptionProsCons
1. Adopt onenote.rs as the sole importer One Rust path can serve the UI and CLI across supported platforms. Its API includes .onetoc2, optional .onepkg, section color, images, embedded files, and ink models. Removing the OfficeIMO bridge may reduce the Windows package payload. Compatibility and content mapping are unverified. MPL-2.0 and transitive dependency obligations need review. The linked Rust code may increase executable size. After cutover, there is no parser fallback; regressions need a fix or deliberate rollback.
2. Consolidate on OfficeIMO Already integrated into the UI and CLI bridge flow. Avoids adopting a new parser dependency and preserves its existing import behavior. Keeps the separately packaged .NET runtime and its Windows payload. The CLI and other supported platforms would need one shared supported route. Its feature coverage still needs verification against NoteCraft requirements.
3. Build and maintain our own parser Least favorable Maximum control over behavior and roadmap. Can follow NoteCraft's clean-room process and avoid taking a third-party parser dependency. Largest engineering and long-term maintenance cost. We must implement and test more of the file formats ourselves, close current gaps such as notebook TOC/package parsing and content fidelity, and carry all compatibility fixes.

The ranking is provisional. The first option is preferred only if it passes the evaluation gates; building our own parser is the least favorable path.

Evaluation gates

  1. Compatibility: run both current routes and the candidate against the same PII-safe synthetic `.one` cases for text, formatting, lists, tables, images, files, ink, missing data, malformed sections, and section color. Compare structural outputs and document intentional differences. This comparison is for development only.
  2. Notebook inputs: separately test `.onetoc2` and `.onepkg` only if the corresponding feature and compliant synthetic fixtures are included. Do not treat `.one` section tests as proof of notebook-package support.
  3. Regression: all existing tests pass unchanged, including `cargo xtask ci`; add assertions for whichever new backend behavior is exposed.
  4. Safety and isolation: malformed input does not panic or abort neighboring imports; sources remain read-only; test data is synthetic and isolated.
  5. License and dependencies: inspect the candidate revision, crate metadata, full dependency license set, notices, update path, and any test-fixture license before distribution or copying test data.
  6. Packaging: compare fresh release artifacts built from the same commit and toolchain: current full package versus a candidate-only package. Record executable, archive, MSI, and install-tree sizes on supported targets.
  7. Decision: if all gates pass, replace both current routes and ship onenote.rs only. If a required gate fails, do not cut over; choose one existing implementation in a revised decision before setting a single-backend release target.
One-backend rule: comparison may use all three implementations in isolated development builds. The target production package uses onenote.rs only; neither the OfficeIMO bridge nor the in-repository parser remains as another product route.

Testing strategy and test data set

A parser migration needs broad, trustworthy regression data. Build a PII-safe synthetic corpus as the primary test set, then add only individually cleared public fixtures for cases that synthetic files cannot represent.

Comprehensive synthetic corpus

Generate small deterministic files from Microsoft's published format specifications and NoteCraft's own test builders. Each case should have a stable identifier, stated feature, expected semantic assertions, and generation recipe. Prefer focused cases that isolate one behavior, plus a small number of composed notebook cases that prove interactions between features.

Valid content and metadata

  • Sections with one or many pages, nested page levels, page order, multiple sections, section groups, and TOC identity mapping.
  • Plain and formatted text, Unicode, mixed direction text, hyperlinks, lists, tables, tags, and page timestamps.
  • Notebook and section colors, pictures, generic attachments, audio/video references, embedded bytes, and native ink where the format builder can represent them.
  • Desktop `.one`, FSSHTTP-based section data, `.onetoc2`, and `.onepkg` as separate format families; include a family only when the candidate feature and tests support it.

Failure and boundary cases

  • Truncated headers, invalid lengths, unknown properties, damaged revisions, malformed TOC entries, and one corrupt section beside a valid section.
  • Missing or invalid attachment data, encrypted sections, duplicate names, Unicode and reserved filenames, and references that do not resolve.
  • Empty sections, very large declared sizes, excessive nesting, and resource limits, with stable skip/error reasons.
  • Verify no panic, no source modification, no silent content drop, and no loss of a valid neighboring section.
Fixture acceptance: the test set contains no owner notebooks, personal names, private content, or copied vendor/source-code samples. Generated bytes and expected results are committed only after privacy review and pass the repository PII scan.

Third-party fixture policy

Credit in a test-set README is not by itself permission to copy a sample. Record provenance, exact license, copyright notice, file hash, privacy review, and permitted use for each third-party file. Preserve the source license in the fixture folder; treat parsed snapshots and extracted attachments as fixture-derived material too.

  • The onenote.rs parser code is MPL-2.0, but its samples have separate terms. Its Joplin corpus is AGPL-3.0-or-later; do not copy it into this dataset. The OneNote 2016 sample set identifies MIT-licensed material from Microsoft's Interop-TestSuites. Other root samples lack clear per-file provenance in the inspected tree.
  • OfficeIMO's library is MIT, but its current fixture provenance file assigns fixture-specific terms: five files copied from Apache Tika under Apache-2.0 with its license and notice, one handwriting file from onenote.rs under MPL-2.0, and a generated synthetic .onepkg. It explicitly excludes the AGPL Joplin samples.
  • MIT and Apache-2.0 files may be candidates for separate redistribution when the exact asset is covered and its license and notices are retained. A recognition README is useful attribution but does not replace those terms. MPL or AGPL assets, and samples with unclear provenance, stay out pending review.
  • The one2html repository is MIT-licensed but its checked-out tree contains no OneNote binary samples. The ConvertOneNote2MarkDown repository is GPL-3.0 and likewise had no tracked .one, .onetoc2, or .onepkg fixtures. Do not copy implementation code from either project into NoteCraft.

Before admitting any public binary fixture, verify its exact source revision, license scope, privacy, and compatibility with NoteCraft's clean-room boundary. Keep cleared public assets separate from generated synthetic fixtures, with per-file provenance, hash, license, copyright, and notice entries. A spec-driven Rust generator is the preferred route for broad coverage; public fixtures are supplemental.

  • Verified in the local candidate checkout: onenote.rs, version 2.1.0, workspace license MPL-2.0; parser feature onepkg enables the optional cab dependency; default feature is native-fs.
  • Existing integration: OfficeIMO is the project behind NoteCraft's currently packaged bridge.

  • Limit: these package files are existing local artifacts and were not freshly rebuilt for this ADR. The candidate has not been integrated, run against NoteCraft tests, or measured in a release package.
  • Test data: do not copy personal notebook files or third-party parser fixtures into the NoteCraft repository without a specific provenance and license check.
